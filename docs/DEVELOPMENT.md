# Fokker F27-500 Modernized (new aircraft, separate package)

A **new, independent package** (`bgt-f27500-modernized`, SimObject `Bgt_F27500v2_Modernized`) that shows up in the sim as its own
aircraft, so the original `bgt-f27500-v2` (and the baseline in `C:\Projetos\f27-efis`) stay untouched: the author's F27-500 with
Working Title WT21 (CJ4 style) avionics and our F27 tablet, whose Settings switch back to the author's Classic cockpit.
Until v10.10 the package was `bgt-f27500-g1000` with two G1000 NXi (WIP) variations from phase 1; v10.11 renamed it and removed them
(user: "Não é G1000, certo? Podia mudar isso"). The project folder keeps its name, `C:\Projetos\f27-g1000`.

## Isolation from the baseline (why nothing collides)
* SimObject folder `Bgt_F27500v2_Modernized` (the baseline's is `Bgt_F27500v2`), unique `[FLTSIM]` titles, package folder
  `bgt-f27500-modernized`. The Community overlay `zz-bgt-f27500-v2` only overrides files under `Bgt_F27500v2`, so it does not touch
  this aircraft.
* The author's systems WASM is only read: the package holds its patched copies under their own names (`WASM_F27WT21.wasm`, and
  `WASM_F27Classic.wasm` with `-ClassicVariation`), never a file of his under its path.
* WT21 files live under `Instruments\F27WT21`, not the sim's `WT21v2`, so they cannot override the CJ4's own avionics.
* Left out of the package: cargo, GPS530 and KLN90B variants and their textures/models, and the author's own `panel` folder (no
  variation uses it: `panel.WT21` is made from his `panel.cfg`).

## What Phase 1 contained (G1000 NXi, removed in v10.11)
* Two variations: "Air Inter 1980 - G1000 NXi (WIP)" (texture it80) and "White - G1000 NXi (WIP)".
* Model variant `model.g1000`: the author's exterior + `F27500v2bgt_INTERIOR_g1000` = author's interior + two 4:3 screens
  (`G1000_PFD_screen`, `G1000_MFD_screen`) cloned from the GNS530 screen quad, materials `$gaugesF27g1000pfd/mfd`.
  The author's own `$gaugesF27gps` material is only a name + emissive factor, so the same trick needs no texture and no binary change.
* Panel variant `panel.G1000`: the author's panel + `[Vcockpit04]` (PFD) and `[Vcockpit05]` (MFD) pointing at the private G1000 copy.
  `panel.xml` only declares power (`CIRCUIT ON:40` / `41` = existing `CIRC_AVIONIC_1/2`).
* Each screen node carries a component with `ASOBO_GT_Material_Emissive_Code` (`EMISSIVE_CODE` = 1). **This is what makes the page
  appear on the 3D material** (proven in-sim, see below); an unpowered G1000 draws its own black screen, so no electrical gating.
* New materials are `{ name, emissiveFactor:[1,1,1] }` (the FSS 727 form), generated by `tools\make-g1000-interior.mjs`.
* **Placement is provisional**: PFD in front of the pilot's ADI_01 (x=+0.4865), MFD at x=+0.03, both at y=0.4066, z=9.12
  (pilot `PILOT_0` is at x=+0.489, z=8.565; panel instruments at z~9.17). They cover real instruments on purpose.

## EIS (engine indication) for the two Dart turboprops (draft, 2026-10-16)
The G1000 NXi draws its engine strip from the classic XML engine display in `panel.xml` (`<EngineDisplay><EnginePage>`, parsed by
`XMLGaugeConfigFactory` in the SDK; tags and gauge types are checked offline by `verify-package.ps1`). Before this there was no
`<EngineDisplay>`, so the strip was empty (the user noticed). `scaffold.ps1` now writes seven `DoubleHorizontal` gauges (one pointer per
engine): TRQ (% of 7800 ft-lb), TGT (L:f275_dart_egt_n_ind), RPM (L:f275_RpmF27_n / 150 = % of 15000 rpm), PROP rpm, FF (pph),
OIL P (psi), OIL T (C). Sources of the variables: engines.cfg, the F27 model XML gauge animations and the WASM strings.
CALIBRATE (guesses until measured in the sim): TGT range 0-1000 and the unit of `L:f275_dart_egt_n_ind`; torque scale (the F27 gauge uses
`L:f275_xengtorq_n_ind`); the RPM green/red zones; zones for PROP/FF/OIL. `tools\devmode\read-engine-vars.mjs [seconds] [interval]` prints
those variables (and the native ones) from the running sim, read-only, to calibrate: sample at cold, idle and take-off power.
The Unit strings use numeric character references (`&#176;C`) because Windows PowerShell 5.1 reads BOM-less .ps1 files as ANSI.

### v10.12: the tablet pulls the aircraft forward (2026-10-28)
* "Teria como colocar uma opção além de empurrar, puxar o avião?": the sim's tug and GSX's only push back. The tug card now has
  Push | Pull; Pull is done by the tablet itself (`plugin-wt21\src\tablet\pull.ts`, `PullTug`), the way pushback tools without a tug
  do it: every frame (the tablet instrument's `Update`) it writes the aircraft's forward speed (`VELOCITY BODY Z`) and yaw rate
  (`ROTATION VELOCITY BODY Y`). 2 kt reached at 0.6 kt/s; up to 3 steering steps of 1°/s each way at full speed (the yaw follows the
  speed, as behind a towbar); Straight; Stop slows to 0, then lets go.
* Live tests in the sim (2026-10-28, SBCT, with the user's OK, Developer Mode, from the tablet's page): 1.5 ft/s written for 2 s moved
  the aircraft 0.89 m straight ahead along its heading; 1.5 "degrees per second" of yaw for 3 s turned the nose 13.9° right
  (4.5°/s: the sim applies three times the rate written in that unit; positive = nose right). `PullTug` divides the yaw it writes by
  the gain it reads back, so the turn is the one asked for. The preview's fake aircraft turns three times the yaw written too, to check
  that (2 steps measured 2.0°/s).
* It does not start with the chocks in or the parking brake set, nor while a tug pushes (the card says which), and it lets go at once if
  the parking brake is set, the wheels leave the ground, the ground speed passes 5 kt, or a tug (the sim's or GSX's) pushes.
* `verify-package.ps1`: the Pull mode in the tablet bundle.
* Installed 2026-10-28 17:04 with v10.11.1 (the user's OK; verify 0 failures on the sources and on `out`; 535 files identical to `out`
  by SHA-256); the v10.11 that was installed is kept in `_fallback\bgt-f27500-modernized-v10.11` (checked identical). The build only

## Debugging with Developer Mode (read-only)
With Developer Mode on, the sim serves the Coherent GT inspector on port 19999 (it accepts connections but answers nothing
while Developer Mode is off). `http://127.0.0.1:19999/pagelist.json` lists the pages; the G1000 shows up as
`VCockpit14 - AS1000_PFD` and `VCockpit15 - AS1000_MFD` (page ids change per session, always re-read the list).
The WebSocket is `ws://127.0.0.1:19999/devtools/page/<id>` (Runtime/Console domains work; `Log` and `Page.captureScreenshot` do not;
`Page.snapshotRect` failed with "Could not capture snapshot").
* `tools\devmode\cdp-probe.mjs <id> [ms]` console + exceptions + a few state checks
* `tools\devmode\cdp-eval.mjs <id> <file>` evaluates the expressions in the file (one per line, `//` comments); read-only by convention
* `tools\devmode\cdp-tick.mjs <id> [ms]` samples instrument counters twice to see if a page is updating
Findings on 2026-10-16 (phase 1, both variations): PFD and MFD pages load from `NavSystems/F27G1000`, our `panel.xml` is parsed
(`Instrument names=AS1000_PFD,AS1000_MFD`), `isVisible=true`, `isElectricityAvailable=true`, `CIRCUIT ON:40/41 = 1`, DOM fully laid
out (HSI, tapes, SVT, softkeys), instrument loop running (~6.7 Hz), no JS exception. One `404` resource error on each page (URL
unknown; the Navigraph G1000 plugin also loads into our instrument because it targets `AS1000_PFD`). So the black 3D screens are NOT a
G1000/JS failure; the page-to-material path (or boot timing) is what to examine.

## Black 3D screens: diagnosis and result (2026-10-16)
Symptom: PFD/MFD pages were alive and correct (inspector + the sim's own pop-out), the engine recognised the screens (zoom button on
hover, panel `quality` medium -> ultra) but the picture on the 3D material stayed black. Control variations (script archived in
`toolshistoryadd-control-variants.ps1`) each changed one suspect. Material A = clone of the author's `$gaugesF27gps` (has a base
colour factor); material B = `{ name, emissiveFactor:[1,1,1] }` (white default base colour: unbound = white, bound but blank = black).

| Variation | Model | Panel | Result |
|---|---|---|---|
| original G1000 NXi it80 / White | material A + `ASOBO_GT_Component_Emissive_Gauge` + `ASOBO_GT_Visibility` (gated on CIRCUIT ON:40/41) | G1000 | black |
| CTRL1 | material A, no components | G1000 | black |
| **CTRL2** | **material B + `ASOBO_GT_Material_Emissive_Code` = 1 (FSS 727 pattern)** | G1000 | **works (PFD and MFD)** |
| CTRL3 | material B, no components | G1000t1 (WT530 in the PFD slot, G1000 MFD) | black (both slots) |
| CTRL4 | base model (author's own GPS530) | author's panel.GPS | did not show the WT530 either |

Conclusion: an explicit `ASOBO_GT_Material_Emissive_Code` component on each screen node is required in this package; with no component
(CTRL1, CTRL3) or with `Component_Emissive_Gauge` + `Visibility` the page does not reach the material. Not separated: whether material B
is also necessary (material A was never tried together with `Material_Emissive_Code`). CTRL4 failing means the author's own GPS530
mechanism does not work inside this (2024-stamped) package either; whether it works in the original package was not checked.
The 2024 docs say `texture=` should not use a `$` prefix any more (it now marks collision materials), yet the legacy F27/FSS 727 and
2024-native third-party aircraft (FNX A320, iniBuilds A350) still use it, so `$` is not the culprit here.

Build log: with the simulator OPEN the package tool exited after 14 s without creating anything (and without a log); right after the sim
was closed the same script built 520 files in 43 s. So close MSFS before `build-package.ps1` and `deploy-community.ps1`.
